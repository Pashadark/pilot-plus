# Pilot+ — гид по проекту

## 1. Паспорт проекта

**Название:** Pilot+  
**Создатель и владелец:** Павел Седов  
**Никнейм:** Pashadark  
**Тип продукта:** коммерческая платформа управления автопарком и транспортной телематикой.

Pilot+ задуман как единый центр управления транспортом. Система должна показывать текущее положение и состояние автомобилей, принимать телеметрию от устройств, хранить историю, выявлять события и помогать компаниям управлять автопарком.

Основные направления продукта:

- оперативный дашборд;
- онлайн-карта автомобилей;
- транспорт и установленное оборудование;
- история поездок и маршрутов;
- тревоги и события;
- геозоны;
- техническое обслуживание;
- аналитика и отчётность;
- уведомления;
- пользователи, компании и роли;
- журнал действий и настройки.

## 2. История технического решения

Изначально рассматривался вариант CSS Modules без Tailwind. От него отказались: окончательное решение — использовать **Tailwind CSS**, но сохранить строгую модульность большого проекта и собственную дизайн-систему.

Ключевые принципы:

- никаких Bootstrap-подобных универсальных UI-фреймворков;
- Tailwind используется как инструмент стилизации, а не как замена архитектуры;
- компоненты разделяются по ответственности и доменным модулям;
- визуальный язык Pilot+ строится на собственных токенах и компонентах;
- светлая и тёмная темы должны работать через CSS variables и дизайн-токены;
- сторонние UI-заготовки допустимы только как техническая основа, внешний вид и API компонентов остаются под контролем проекта.

В раннем плане упоминались Next.js 15, shadcn/ui, Zustand, TanStack Query, Axios, Zod, React Hook Form, react-map-gl, Socket.IO, Lucide, Recharts, next-themes и date-fns. Это **целевой/исторический план, а не список уже установленных библиотек**. Перед добавлением каждой зависимости нужно подтвердить, что она действительно нужна.

## 4. Текущее состояние продукта

### Что работает

- главная страница App Router;
- desktop-layout с header и sidebar;
- шесть компактных карточек сводной статистики;
- плотная лента последних событий;
- демонстрационные графики пробега и расхода топлива;
- MapLibre-карта Москвы;
- три демонстрационных автомобиля;
- изменение подробности маркеров в зависимости от zoom;
- выбор автомобиля, приближение карты и открытие панели;
- production build и строгая проверка TypeScript;
- собственная дизайн-система Pilot+ с семантическими токенами, светлой и тёмной темами;
- исполняемая витрина компонентов на маршруте `/ui-kit`;
- адаптивная оболочка с desktop-sidebar и доступным мобильным drawer;
- полноэкранное мобильное рабочее пространство карты с поиском, фильтрами и нижней панелью автомобиля;
- Playwright-проверки маршрутов, клавиатурной доступности, touch targets и основных responsive-сценариев;
- локальная инфраструктура PostgreSQL/PostGIS, Redis и Mosquitto;
- подключение Prisma к PostgreSQL.
- публичная адаптивная форма `/login` в светлой и тёмной темах;
- серверный вход и выход администратора через Next.js Server Actions;
- пароли `scrypt`, непрозрачные 32-байтовые session tokens и хранение только SHA-256-хеша токена;
- cookie `pilot-session` с HttpOnly, SameSite=Lax, Path=/, семидневным сроком и Secure в production;
- защита `/` и `/ui-kit` серверным route-group layout;
- блокировка email на 15 минут после пяти последовательных ошибок;
- Prisma-модели `User`, `Session`, `LoginThrottle`, SQL-миграция и идемпотентный seed;
- tenant-модели `Company` и `CompanyMember`, связывающие администратора с его данными;
- доменные модели `Vehicle`, `VehiclePosition`, `Trip`, `VehicleEvent`, `FuelRecord`, `MaintenanceRecord` и `VehicleDocument`;
- идемпотентный импорт 130 автомобилей из предоставленного каталога в PostgreSQL;
- защищённый маршрут `/vehicles` с поиском, фильтрами и адаптивными карточками;
- защищённый маршрут `/vehicles/[id]` с обзором и семью адресуемыми вкладками;
- честные пустые состояния пробега, топлива, GPS, поездок, маршрутов, событий, обслуживания и документов;
- глобальные тост-уведомления `success`, `warning`, `danger`, `info` справа сверху и на всю доступную ширину телефона;
- 49 unit-тестов auth/core/database/vehicles/toasts и browser-проверки автопарка и UI-kit.

### Что является демонстрацией

Бизнес-данные дашборда и карты сейчас являются типизированными fixtures. Поиск и фильтры на мобильной карте работают только с этими демонстрационными данными. Раздел автомобилей уже читает PostgreSQL, но импортированный каталог содержит характеристики и цену без госномеров, VIN, координат и телеметрии. Поэтому отсутствующие показатели не заменяются случайными значениями. Выбор компании, аккаунт, редактирование автомобиля и бронирование ещё не выполняют прикладных операций.

В локальную PostgreSQL применены миграции авторизации, tenant-модели, транспорта и будущей истории. Телематические таблицы созданы, но остаются пустыми до подключения реального ingestion-потока. Redis и MQTT определены в Compose, но приложение к ним ещё не подключено.

### Известный технический долг

- существуют два каталога сгенерированного Prisma-клиента;
- реальный путь generated-кода не совпадает с правилом `.gitignore`;
- конфигурация Prisma в `package.json` устаревает перед Prisma 7;
- production build предупреждает о чрезмерно широком NFT trace через сгенерированный `prisma-client-js`;
- старый Playwright-набор дашборда не создаёт авторизованное storage state и должен быть переведён на общий auth fixture;
- локальный администратор создан, но CI/test environment всё ещё требует собственные безопасные auth-переменные;
- CI пока не настроен, хотя локальные e2e-тесты уже добавлены;
- production-провайдер тайлов карты ещё не выбран; текущая OpenStreetMap raster-конфигурация предназначена для прототипа;
- error/retry MapLibre пока проверяется статически и через build, без детерминированного e2e test seam;
- диагностические скрипты печатают `.env`, а `check-db.ps1` запускает изменяющий схему `prisma db pull`.

│   ├── dashboard/
│   ├── map/
│   ├── vehicles/
│   ├── devices/
│   ├── history/
│   ├── events/
│   ├── geofences/
│   ├── reports/
│   ├── maintenance/
│   ├── users/
│   ├── companies/
│   └── settings/
├── shared/
│   ├── components/      # общие составные компоненты
│   ├── ui/              # низкоуровневая UI-библиотека Pilot+
│   ├── hooks/
│   ├── lib/
│   ├── types/

├── services/            # клиенты и интеграции с внешними системами

Часть этой структуры пока существует только как направление развития. Не нужно создавать пустые каталоги заранее: модуль появляется вместе с реальной функциональностью.

### Границы модулей

Каждый доменный модуль может содержать:

```text
modules/vehicles/
├── components/
├── server/
├── hooks/
├── schemas/
├── types/
└── index.ts
```

Правила зависимостей:

- `app` собирает страницы из модулей и shared-компонентов;
- модуль не импортирует внутренние файлы другого модуля;
- общий код переносится в `shared` только после появления реального повторного использования;
- доступ к БД выполняется только на сервере;
- Prisma-клиент нельзя импортировать в Client Components;
- внешние интеграции изолируются в `services` или server-части модуля;
- публичный API модуля экспортируется через `index.ts`, когда это действительно упрощает границы.

### Server и Client Components

По умолчанию компоненты должны оставаться серверными. Директива `"use client"` нужна только при наличии:

- state/effect/ref;
- browser API;
- event handlers;
- клиентской анимации;
- MapLibre или другой browser-only библиотеки.

Карту, интерактивные фильтры и панели следует делать клиентскими островами. Страницы, загрузку данных и статическую разметку — серверными.

## 6. Дизайн-система

Текущее визуальное направление Pilot+ основано на утверждённом макете телематического dashboard-сервиса: холодный серый canvas, белые поверхности, синий основной акцент, широкая светлая боковая панель, шесть KPI и аналитическая сетка вокруг главной карты. Это оригинальная адаптация под Pilot+, а не перенос чужого бренда или бизнес-компонентов. Карта, телематика и продуктовые сценарии остаются собственными Pilot+.

Актуальные базовые цвета из `src/app/globals.css`:

- primary light: `#2563EB`;
- primary dark: `#818CF8`;
- light canvas: `#F3F4F6`;
- light surface/card: `#FFFFFF`;
- light text: `#1F2937`;
- secondary text: `#6B7280`;
- light border: `#E5E7EB`;
- dark canvas: `#111827`;
- dark surface/card: `#1F2937`;
- dark border: `#374151`.

Цель — компоненты `Button`, `Input`, `Card`, `Modal`, `Table`, `Sidebar`, `Header`, `Tabs`, `Badge`, `Tooltip` и другие примитивы Pilot+. Компоненты должны использовать семантические CSS variables или общие варианты, а не повторять hex-цвета по всему коду.

Темы должны переключаться атрибутом или классом на корневом элементе. Компоненты не должны содержать отдельную бизнес-логику для светлой и тёмной темы.

## 7. Поток данных и инфраструктура

Локальные сервисы определены в `compose.yaml`:

| Сервис              | Назначение                           | Локальный порт |
| ------------------- | ------------------------------------ | -------------- |
| PostgreSQL/PostGIS  | доменные данные, история и геоданные | 5433           |
| Redis               | актуальное состояние, кэш, pub/sub   | 6379           |
| Mosquitto           | приём MQTT-телеметрии                | 1883           |
| Mosquitto WebSocket | MQTT для совместимых web-клиентов    | 9001           |

Целевой путь телеметрии:

```text
GPS/IoT device
    → MQTT broker
    → ingestion worker
    → validation and normalization
    → PostgreSQL/PostGIS (history)
    → Redis (latest state / pub-sub)
    → SSE or WebSocket gateway
    → Pilot+ map and dashboard
```

Клиентский браузер не должен быть единственным потребителем MQTT и не должен самостоятельно сохранять телеметрию. Нужен серверный worker с повторной обработкой, логированием и идемпотентностью.

### Планируемый Telegram-бот гаража

Для водителей и диспетчеров запланирован отдельный асинхронный Telegram-бот на Python 3.12+, aiogram 3, SQLAlchemy 2 и PostgreSQL. Он должен принимать подачу, выдачу, возврат, мойку, заправку и перегон автомобиля через кнопки или свободный текст, собирать фотографии, рассчитывать доплаты и синхронизировать заявки с Pilot+ API.

Полная продуктовая и техническая концепция сохранена в [`docs/ideas/BOT_ARCHITECTURE.md`](ideas/BOT_ARCHITECTURE.md). Это утверждённое направление, но не уже реализованный модуль: код бота, его таблицы и Pilot+ API пока отсутствуют.

## 8. Предварительная доменная модель

Первая версия модели должна включать:

- `Company` — организация-владелец данных;
- `User` и членство пользователя в компании;
- `Role`/permissions;
- `Vehicle` — транспортное средство;
- `Device` — телематическое устройство;
- `Position` — координаты и состояние в момент времени;
- `Trip` — рассчитанная поездка;
- `Event` — тревога или значимое событие;
- `Geofence` — геозона с геометрией PostGIS;
- `Maintenance` — обслуживание и регламент;
- `Notification` — доставка события пользователю;
- `AuditLog` — действия пользователей и системы.

Все доменные сущности должны учитывать tenant/company boundary. Доступ к данным другой компании запрещён на серверном уровне, а не только скрыт в интерфейсе.

До реализации схемы нужно отдельно согласовать формат входящей телеметрии, частоту сообщений, правила хранения истории и модель ролей.

## 9. Команды разработки

```powershell
# установка
npm install

# инфраструктура
docker compose up -d
docker compose ps
docker compose down

# приложение
npm run dev
npm run build
npm run start

# проверки
npm run lint
npm run test:unit
npm run test:e2e:auth
npx playwright test tests/vehicles.spec.ts --workers=1
npx tsc --noEmit
npx prettier --check "src/**/*.{ts,tsx,css}"
npx prisma validate
npx prisma migrate deploy
npm run db:seed
```

`npm run build` в Next.js 16 не заменяет ESLint. В CI эти проверки должны выполняться отдельными шагами.

Перед изменением Next.js-кода необходимо читать релевантный локальный гайд из `node_modules/next/dist/docs/`: установленная версия содержит отличия от старых Next.js API и соглашений.

## 10. Правила разработки

1. Не менять архитектуру или стек только на основании старого плана — сначала сверяться с фактическим репозиторием.
2. Не добавлять зависимость без конкретного использования.
3. Не редактировать сгенерированный Prisma-клиент вручную.
4. Любое изменение Prisma schema сопровождается миграцией.
5. Не выводить секреты и содержимое `.env` в логи.
6. Не использовать `any`, если тип можно вывести или описать.
7. UI должен быть адаптивным и доступным с клавиатуры.
8. Навигация делается ссылками, действия — кнопками, поиск — полем ввода.
9. Внешние запросы должны иметь loading, empty и error states.
10. Новая функциональность считается готовой после lint, typecheck, тестов и production build.
11. Демонстрационные данные должны явно называться fixtures/mocks и не смешиваться с production-потоком.
12. Сначала реализуется вертикальный сценарий целиком, затем расширяется количество экранов.
