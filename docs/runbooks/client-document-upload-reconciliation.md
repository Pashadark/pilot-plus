# Reconciliation зависших загрузок документов и фото клиентов

Команда переводит просроченные `UPLOADING`/`PENDING` версии в недоступный `ERROR`,
сохраняет текущую CLEAN-версию при неуспешной замене и удаляет только связанные с
зависшей попыткой файлы. Непроверенный файл никогда не продвигается.
Для фото worker по tenant-scoped DB-состоянию сохраняет уже закоммиченный final object и
удаляет только source/normalized artifacts; незакоммиченный final удаляется.

## Запуск

После применения штатной миграции deployment-процессом задайте server-only переменные
`DATABASE_URL` и `PRIVATE_STORAGE_ROOT`, затем выполните:

```powershell
npm run client-documents:reconcile
```

Команда не содержит встроенного cron. В production её можно вызывать внешним scheduler
каждые 5–10 минут или вручную после аварийного завершения процесса.

Порог lease задаёт `CLIENT_DOCUMENT_STALE_UPLOAD_MINUTES`. Значение по умолчанию — 15
минут, допустимые границы — от 5 минут до 24 часов. Старые строки rolling deployment без
lease обрабатываются по `createdAt` и тому же порогу. Один запуск обрабатывает не более
100 строк каждого типа. Если команда завершилась с exit `2` и сообщила о необработанных
строках, повторяйте её, пока такое сообщение не исчезнет. Параллельные запуски
безопасны благодаря conditional claim.

## Результат

- exit `0`: текущая page reconciliation завершена, `hasMore=false`, отложенной очистки нет;
- exit `2`: есть следующая page и/или storage-очистка отложена до retry lease; повторите запуск
  сразу для page или после порога retry для отложенной очистки;
- exit `1`: запуск не завершён; проверьте `DATABASE_URL`, `PRIVATE_STORAGE_ROOT`, права
  хранилища и доступность БД, затем повторите.

Каждая впервые восстановленная версия получает системный `SCAN/ERROR` audit без имени,
пути, байтов или PII. Replacement не меняет текущую CLEAN-версию. Online worker не
делает глобальный mtime sweep: после conditional claim он удаляет только quarantine,
`scan-*` и `normalized-*` artifacts, имя которых точно содержит claimed durable `uploadId`.
Поэтому snapshot активной загрузки с успешным heartbeat не удаляется даже при старом mtime,
а crash-orphan удаляется по связанной durable DB-записи.
