# Рейтинг надёжности клиента

## Назначение

Рейтинг — объяснимый сигнал для сотрудников, а не автоматический запрет аренды. Итог равен
`clamp(55 + SUM(ClientRatingEvent.delta), 0, 100)`. Он отображается как пять всегда видимых
звёзд, число и текстовый уровень. Не записывайте в события, аудит или описания паспортные данные,
телефоны, адреса либо расшифрованные документы.

## Развёртывание

Миграция `20260822120000_add_client_rating` аддитивно добавляет статусы проблем, поля заметок и
append-only таблицу `ClientRatingEvent`. До production rollout сделайте отдельную резервную копию
PostgreSQL. Затем на целевой базе, только из deployment job, выполните:

```powershell
npx prisma migrate deploy
npx prisma generate
```

Не выполняйте `prisma migrate dev`, `db:seed`, reset или эту миграцию против общей базы из E2E,
локального review или тестового запуска. Откат приложения выполняется кодом, который умеет читать
новые nullable поля; SQL-откат таблицы или enum-значений не выполняйте, пока журнал содержит
данные. При необходимости остановите создание новых rating events, сохраните backup и подготовьте
отдельную проверенную migration для будущего удаления после согласованной retention-процедуры.

## Правила оценки

Новый клиент начинает с 55 баллов (3 звезды, «Рейтинг формируется»). Подтверждённая чистая
завершённая аренда даёт `+8`, своевременный возврат — `+2`, а подтверждённый просроченный
неоплаченный штраф — `-15`. Ручная заметка может дать от `+1` до `+10` либо от `-1` до `-30`;
нулевое значение запрещено. Неподтверждённые кандидаты штрафов и ошибки синхронизации рейтинг не
меняют.

Автоматические записи используют ключи `rental:<id>:clean-completion`,
`rental:<id>:on-time-return` и `fine:<id>:confirmed-overdue`. Повтор операции с тем же ключом
должен быть no-op. Журнал неизменяем: триггер PostgreSQL запрещает `UPDATE` и `DELETE`.

## Роли и работа с проблемой

`SUPER_ADMIN`, `COMPANY_ADMIN` и `DISPATCHER` могут видеть рейтинг и создавать внутренние
заметки своей компании. Только `SUPER_ADMIN` и `COMPANY_ADMIN` могут создать ручное влияние на
рейтинг или скрыть произвольную заметку. `DRIVER` и `VIEWER` не получают внутренние заметки и
объяснения рейтинга.

Чтобы решить проблему, откройте карточку клиента, найдите видимую заметку со статусом «Открыта» и
нажмите «Решить». Это меняет только lifecycle заметки на «Решена» и пишет аудит; историческое
рейтинговое событие остаётся неизменным. Чтобы компенсировать прежнее влияние, администратор
создаёт новую положительную или отрицательную заметку с включённым «Учитывать в рейтинге» и
обязательной причиной — не редактирует прежний event.

## Read-only проверка журнала

В текущей схеме кэшированного score нет. Если он появится, сравнивайте его с ledger sum только
read-only запросом (замените `cached_score` именем согласованной колонки):

```sql
SELECT
  c."id" AS client_id,
  LEAST(100, GREATEST(0, 55 + COALESCE(SUM(e."delta"), 0))) AS ledger_score,
  c.cached_score
FROM "Client" AS c
LEFT JOIN "ClientRatingEvent" AS e
  ON e."companyId" = c."companyId" AND e."clientId" = c."id"
WHERE c."companyId" = :company_id
GROUP BY c."id", c.cached_score
HAVING c.cached_score IS DISTINCT FROM LEAST(100, GREATEST(0, 55 + COALESCE(SUM(e."delta"), 0)));
```

Run it with a read-only database role and the actual tenant identifier. Do not use this diagnostic
query to update scores or repair ledger history.
