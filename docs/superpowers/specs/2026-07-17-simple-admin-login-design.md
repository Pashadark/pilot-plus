# Pilot+ — безопасный вход администратора

**Статус:** утверждено Павлом Седовым 17 июля 2026 года  
**Задача Notion:** «Сделай логин форму и ригистрацию»  
**Объём первой версии:** вход и выход одного администратора; регистрация и приглашения отложены.

## Цель

Добавить в Pilot+ простую серверную авторизацию по email и паролю. Первый администратор создаётся воспроизводимой seed-командой. Рабочие маршруты приложения недоступны без действующей серверной сессии.

## Границы задачи

В первую версию входят:

- создание первого администратора из переменных окружения;
- форма входа `/login` в визуальном стиле Pilot+/Mosaic;
- проверка email и пароля только на сервере;
- серверная сессия в PostgreSQL;
- безопасная cookie с непрозрачным случайным токеном;
- защита `/` и `/ui-kit`;
- выход с отзывом текущей серверной сессии;
- временная блокировка после серии неудачных попыток;
- адаптивность, клавиатурная доступность и светлая/тёмная темы.

В первую версию не входят:

- публичная регистрация;
- приглашения сотрудников;
- восстановление и изменение пароля;
- двухфакторная авторизация;
- социальные провайдеры;
- полная ролевая модель и интерфейс управления пользователями.

## Модель данных

Доменная схема расширяется минимальными сущностями авторизации без изменения существующих продуктовых данных.

### User

- `id` — стабильный идентификатор;
- `email` — нормализованный уникальный email;
- `name` — отображаемое имя;
- `passwordHash` — результат `scrypt` вместе с параметрами и солью;
- `role` — первая версия поддерживает только `ADMIN`;
- `isActive` — возможность запретить вход без удаления пользователя;
- `createdAt`, `updatedAt`.

### Session

- `id` — идентификатор записи;
- `userId` — владелец сессии;
- `tokenHash` — SHA-256-хеш случайного токена, а не сам cookie-токен;
- `expiresAt` — срок действия семь дней;
- `createdAt`;
- индекс по `tokenHash` и каскадное удаление вместе с пользователем.

### LoginThrottle

- ключ нормализованного email;
- число последовательных ошибок;
- время последней ошибки;
- `lockedUntil` для временной блокировки.

После успешного входа счётчик удаляется. После пяти последовательных ошибок вход блокируется на пятнадцать минут. Ответ остаётся одинаковым для отсутствующего пользователя, неверного пароля, неактивной записи и временной блокировки.

## Пароли и seed

Seed читает:

- `PILOT_ADMIN_EMAIL`;
- `PILOT_ADMIN_PASSWORD`;
- `PILOT_ADMIN_NAME`.

Команда завершается с понятной ошибкой, если обязательные значения отсутствуют или пароль не соответствует минимальным требованиям. Seed идемпотентен: повторный запуск обновляет имя и безопасно заменяет пароль существующего администратора, но не создаёт дубликат.

Пароль:

- минимум 12 символов;
- хешируется встроенным Node.js `crypto.scrypt`;
- получает новую случайную соль при каждом сохранении;
- сравнивается через `timingSafeEqual`;
- никогда не записывается в логи, клиентский JavaScript или Notion.

## Сессия

После успешной проверки создаётся криптографически случайный токен не менее 256 бит. Клиент получает исходный токен, PostgreSQL — только SHA-256-хеш.

Cookie `pilot-session` имеет:

- `HttpOnly`;
- `SameSite=Lax`;
- `Secure` в production;
- `Path=/`;
- срок действия семь дней.

Каждый защищённый серверный маршрут проверяет наличие записи сессии, срок действия, активность пользователя и роль. Недействительная cookie удаляется. Выход удаляет запись сессии и cookie.

## Маршруты и поток

### `/login`

Публичный маршрут. Форма содержит email, пароль, кнопку «Войти» и доступное сообщение об ошибке. Уже авторизованный пользователь перенаправляется на `/`.

### `/` и `/ui-kit`

Защищённые маршруты. Неавторизованный запрос перенаправляется на `/login`. Серверные проверки остаются источником истины; скрытие элементов на клиенте не считается защитой.

### Выход

Доступен из меню профиля. Server Action отзывает текущую сессию и перенаправляет на `/login`.

## Архитектурные границы

- `src/modules/auth/` содержит формы, server actions, схемы входных данных и прикладные правила.
- `src/services/auth/` содержит хеширование паролей и управление токенами/сессиями.
- `src/database/` остаётся единственной точкой Prisma client и схемы.
- DAL-функция возвращает только безопасный DTO пользователя и централизует проверку сессии.
- UI использует существующие `Button`, `Input`, `Card`, `Alert` и дизайн-токены; локальная копия компонентов не создаётся.

## Ошибки и безопасность

- Форма не сообщает, существует ли email.
- Входные значения нормализуются и проверяются до обращения к БД.
- Server Action не принимает роль или идентификатор пользователя от клиента.
- Redirect разрешён только на внутренний заранее определённый маршрут `/`.
- Ошибки БД не раскрываются пользователю.
- В production отсутствие безопасных переменных окружения блокирует seed и запуск auth-конфигурации.
- Сессии с истёкшим сроком считаются недействительными и могут удаляться при проверке.

## Проверки

Обязательные автоматические сценарии:

- seed создаёт администратора и не создаёт дубликаты;
- пароль не хранится открыто и корректно проверяется;
- правильные данные создают сессию и защищённую cookie;
- неверные данные возвращают одинаковую ошибку;
- пять ошибок включают блокировку, успешный вход сбрасывает счётчик;
- гость перенаправляется с `/` и `/ui-kit` на `/login`;
- авторизованный администратор видит дашборд;
- выход отзывает сессию и снова закрывает маршруты;
- форма работает с клавиатуры, не переполняется на 375 px и поддерживает обе темы;
- lint, typecheck, format, production build и полный Playwright проходят.

## Критерии готовности

Задача готова, когда администратор воспроизводимо создаётся seed-командой, может войти и выйти, неавторизованный пользователь не получает рабочие маршруты, защита подтверждена тестами, а секреты отсутствуют в Git и логах.
