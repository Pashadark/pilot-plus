# Живая карта GLONASSSoft

Дата: 23 августа 2026 года
Статус: согласовано с владельцем продукта

## Цель

Показывать движение десяти реальных автомобилей Pilot+ на карте почти в реальном времени. Ожидаемая задержка между появлением новой позиции в GLONASSSoft и её отображением в Pilot+ — 2–4 секунды плюс задержка GPS-терминала.

## Границы

- Источник данных — существующая интеграция GLONASSSoft Public API v3.
- Один серверный worker запрашивает последние данные всех связанных автомобилей одним пакетным запросом каждые 2 секунды.
- Браузер не обращается к GLONASSSoft и не получает его учётные данные.
- Новые позиции сохраняются идемпотентно в PostgreSQL.
- Сохранённые изменения немедленно передаются открытым картам через серверный SSE-канал.
- Карта продолжает показывать последний известный снимок при временной ошибке провайдера.
- Эта работа не меняет договоры, клиентов, штрафы и Telegram-бота.

## Архитектура

### GPS-worker

Отдельный долгоживущий Node.js-процесс запускается на VPS под `systemd`. Он использует существующую таблицу включённых телематических интеграций и существующие привязки автомобилей.

Цикл worker:

1. Загружает включённые компании GLONASSSoft.
2. Для каждой компании вызывает существующую синхронизацию последних позиций.
3. Передаёт все внешние идентификаторы компании одним запросом `vehicles/getlastdata`.
4. Сохраняет только новые сообщения через существующий идемпотентный ключ позиции.
5. Публикует компактное событие об изменившихся автомобилях в Redis.
6. Ждёт до следующего двухсекундного такта, учитывая длительность запроса; параллельные циклы запрещены.

Worker использует одну авторизованную API-сессию повторно, соблюдает ограничения GLONASSSoft и применяет ограниченную экспоненциальную задержку при `429`, timeout и недоступности провайдера. Ошибка одной компании не останавливает процесс.

### SSE-шлюз

Защищённый tenant-scoped маршрут Next.js открывает `text/event-stream` только после проверки активной сессии и доступа к карте. Он:

- отправляет начальный снимок из PostgreSQL;
- подписывается на tenant-канал Redis;
- передаёт только DTO карты без секретов и лишних персональных данных;
- посылает heartbeat и корректно освобождает подписку при закрытии соединения;
- не кэшируется прокси или браузером.

Если Redis временно недоступен, маршрут завершается, а клиент переподключается и получает новый снимок из базы.

### Клиент карты

После гидратации карта открывает `EventSource`. При событии она заменяет состояние соответствующего автомобиля, плавно перемещает маркер и обновляет скорость, адрес, пробег, топливо и время сигнала без перезагрузки страницы.

При обрыве используется встроенное повторное подключение с ограниченной задержкой. Существующее правило состояния остаётся единым: свежий сигнал считается подключённым; отсутствие обновлений более 15 минут отображается красным статусом «Нет связи».

## Конфигурация и эксплуатация

На VPS создаётся отдельный защищённый env-файл процесса. В нём находятся URL внутреннего приложения, служебный токен, ключ расшифровки и параметры Redis. Значения не попадают в Git, интерфейс или логи.

`systemd` запускает worker после сети и базы, автоматически перезапускает его после сбоя и поднимает после перезагрузки VPS. Логи содержат только безопасные коды, число компаний, запрошенных и сохранённых позиций, время цикла и возраст последнего успеха.

## Ошибки и защита

- Не запускать новый цикл, пока предыдущий не завершён.
- Не удалять последнюю позицию при ошибке API.
- Не публиковать событие, если позиция не изменилась.
- Ограничить размер ответа провайдера, таймаут и число автомобилей в запросе.
- Проверять tenant boundary до чтения снимка и подписки Redis.
- Не передавать наружу логины, пароли, токены, внешние ответы и внутренние коды компаний.
- При продолжительной ошибке отображать последнюю позицию и честный красный статус связи.

## Проверка готовности

Автоматические тесты должны доказать:

- двухсекундный цикл не перекрывается сам с собой;
- повторная позиция не создаёт запись и событие;
- новая позиция сохраняется и публикуется;
- сбой API вызывает безопасный backoff и не стирает данные;
- SSE требует авторизацию и изолирует компании;
- heartbeat и закрытие соединения освобождают ресурсы;
- карта применяет событие без перезагрузки и пересчитывает GPS-статус;
- обрыв канала не ломает последний снимок.

Ручная приёмка выполняется на реальной машине: открыть Pilot+ и Sputnik Vision одновременно, начать движение, подтвердить обновление маркера Pilot+ с задержкой не более 4 секунд после появления новой точки у провайдера, затем проверить восстановление после перезапуска worker.

## Критерий завершения

Функция готова, когда worker автоматически работает на VPS, новые координаты поступают в PostgreSQL, открытая карта получает их через SSE без перезагрузки, статусы связи честно меняются, а процесс восстанавливается после перезагрузки сервера.
