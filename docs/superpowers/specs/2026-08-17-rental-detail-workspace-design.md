# Pilot+ — полноценная карточка договора аренды

## Цель

Превратить `/rentals/[id]` из технической сводки в полноценное рабочее место договора аренды. Экран должен показывать все реально сохранённые сведения, корректно обрабатывать старые импортированные записи и использовать общую дизайн-систему Pilot+.

## Границы этапа

В этап входит только карточка отдельной аренды, связанные серверные проекции, состояния загрузки и тесты. Общий аудит размеров кнопок и типографики всего проекта выполняется отдельным этапом после завершения карточки.

Этап не изменяет существующие договорные суммы и не создаёт вымышленные документы, адреса или записи аудита для исторических импортов.

## Идентификаторы и заголовок

- Основной заголовок — бизнес-номер договора, например `ME-2026-0001-BK`.
- Технический ID PostgreSQL показывается всем сотрудникам рядом с номером договора.
- Рядом с техническим ID располагается доступная кнопка «Копировать ID» с success-toast.
- Статус показывается русским Badge: «Черновик», «Подтверждён», «Активен», «Завершён» или «Отменён».
- В заголовке доступны возврат к списку, переход к клиенту и переход к автомобилю.

## Источник данных

У карточки два режима представления:

1. Для нового подтверждённого договора юридические сведения читаются из неизменяемого snapshot.
2. Для старого импортированного договора недостающие snapshot-поля безопасно дополняются текущими полями самой `Rental`, но интерфейс явно показывает пометку «Импортированный договор».

Статус аренды никогда не определяется по форме snapshot. Завершённая запись со старым snapshot остаётся завершённой, а не называется черновиком.

## Компоновка

### Верхняя сводка

Под заголовком располагаются четыре компактные карточки:

- срок аренды и количество оплачиваемых дней;
- итоговая стоимость;
- залог;
- автомобиль и клиент.

На desktop карточки образуют сетку, на телефоне становятся одной колонкой без горизонтального переполнения.

### Финансы

Отдельная Card показывает:

- суточный тариф;
- оплачиваемые дни;
- базовую стоимость;
- скидку;
- дополнительные услуги;
- итог;
- залог;
- причину ручного изменения цены, если она существует.

Все денежные значения форматируются в рублях из minor units. Отсутствующее значение отображается как «Не указано», а не как ноль.

### Выдача и возврат

Секция показывает две колонки — «Выдача» и «Возврат»:

- плановые даты начала и окончания;
- фактические `activatedAt` и `completedAt`;
- адреса;
- пробег;
- уровень топлива;
- территория использования;
- условия оплаты;
- допущенные водители;
- дополнительные условия.

Для импортированных записей используются только реально доступные значения. Пустые значения получают понятную подпись «Не указано».

### Эксплуатационные условия

Отдельная компактная секция показывает включённый пробег, стоимость перепробега и стоимость недостающего топлива.

### Документы

- CLEAN DOCX/PDF отображаются одинаковыми кнопками загрузки из UI-kit.
- Подготовка и ошибка генерации получают русские статусы.
- Если документов нет, экран объясняет причину: для старого импорта документы не были сформированы либо для подтверждённой записи требуется повторная генерация.
- Система не обещает сформировать юридический документ, если для исторической записи недостаточно обязательных данных.

### Хронология и аудит

Экран разделяет два источника:

- «Этапы аренды» строятся из фактических `createdAt`, `confirmedAt`, `activatedAt`, `completedAt` и `cancelledAt`;
- «История действий» строится только из `AuditLog`.

Если у старого импорта нет аудита, показывается честное пустое состояние. Системные даты не маскируются под действия конкретного пользователя.

## Данные и серверные границы

`getRentalDetailForCurrentUser` остаётся tenant-scoped и выбирает только необходимые поля:

- полную финансовую разбивку `Rental`;
- системные даты жизненного цикла;
- клиентский и автомобильный идентификаторы и безопасные подписи;
- immutable snapshot;
- водителей;
- версии документов и состояния генерации.

Проекция не передаёт зашифрованные паспортные данные, приватные storage keys, password hash или внутренние ошибки конвертера.

Аудит остаётся отдельным tenant-scoped запросом. Английские action-коды переводятся только на уровне представления.

## Компоненты и дизайн-система

Экран собирается из существующих `Card`, `CardHeader`, `CardContent`, `Badge`, `Button`, `PageHeader` и общих семантических токенов. Ссылки-действия получают визуально согласованный link-button компонент либо общий класс на базе тех же размеров.

Правила:

- основной размер интерактивных элементов — `md`, минимальная высота 44 px;
- одинаковые действия имеют одинаковую высоту, радиус и внутренние отступы;
- подписи — не меньше 12 px, основной текст — не меньше 14 px;
- иконки дополняют текст и имеют доступные названия;
- цвет не является единственным носителем статуса;
- светлая и тёмная темы используют существующие CSS variables;
- длинные ID, номера и имена переносятся без горизонтального скролла.

## Loading, empty и error states

- `loading.tsx` повторяет геометрию заголовка, четырёх KPI и основных секций.
- Отсутствующие документы, аудит и условия получают отдельные пустые состояния.
- Неверный или чужой ID возвращает 404 без раскрытия существования чужой записи.
- Ошибка загрузки остаётся в существующем фирменном error boundary.

## Проверки

Unit-тесты должны подтверждать:

- русские статусы;
- отображение технического ID;
- финансовую разбивку и залог;
- корректный fallback старого импортированного snapshot;
- различие фактической хронологии и AuditLog;
- документы и их пустые состояния;
- отсутствие строк `undefined`, `null` и английских enum в UI;
- mobile-safe структуру и единые размеры кнопок.

Интеграционная проверка использует договор `ME-2026-0001-BK` и подтверждает показ залога 15 000 ₽, тарифа 4 700 ₽/сутки, двух дней, итога 9 400 ₽ и завершения 14.08.2026 без создания вымышленных документов или аудита.

Перед завершением выполняются целевые тесты, `npm run typecheck`, `npm run lint`, полный unit-набор и `npm run build`.

## Критерии готовности

- сотрудник понимает состояние договора без обращения к базе;
- все реально сохранённые суммы, сроки и эксплуатационные условия видны;
- номер договора и технический ID различимы и копируются;
- старые импорты не называются черновиками из-за сокращённого snapshot;
- документы и история не подменяются вымышленными данными;
- экран одинаково удобен на desktop и телефоне;
- элементы соответствуют UI-kit Pilot+.
